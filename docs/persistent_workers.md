# Persistent generation workers (design proposal)

Status: **proposal — not implemented.** This documents the per-profile overhead in
VULCAN-JAX data generation and the design I'd use to fix it. It deliberately stops
short of code.

## Scope

This is about the **generation** stage only (`--stage generation`), specifically the
`vulcan.runtime.backend = "vulcan_jax"` path used by the 100k Luhman 16A dataset
(`config/vulcan_luhman16a_100k.json`), running on a single 72-core GH200 node. It does
not touch normalization, training, export, the `master` backend, or sharding.

## The problem: one OS process per profile

Today each profile is generated by launching a **fresh Python subprocess**:

- `src/data_generation/generation.py::_run_single_vulcan_jax_spec` (~L2083) runs, per
  profile: prepare/reset the worker tree, write the TP + spectrum inputs, patch a
  per-run `vulcan_cfg.py`, then `subprocess.run([python, "-m",
  "vulcan_jax.vulcan_jax_cli"])` (~L2113–2119, with `JAX_PLATFORMS=cpu`).
- A `ThreadPoolExecutor` of `generation.parallel_workers` (=72) keeps 72 such
  subprocesses in flight at once. Each finished `.vul` is read back and converted to a
  per-run HDF5 in `raw/runs/`, then folded into `raw/chunks/` (consolidation is a
  separate single-worker executor), and finally merged to `raw/runs.h5`.

Every subprocess pays a **fixed startup cost that has nothing to do with the chemistry**:

1. Python interpreter start.
2. `import jax` (heavier now that `jax[cuda12]` + ~3 GB of NVIDIA libs are installed;
   `JAX_PLATFORMS=cpu` avoids GPU init, but the base import is still ~1–2 s).
3. `import vulcan_jax` → `chem_funs.py:29` runs `build_chem_rhs(_NETWORK)` at import. The
   generated source is content-hash cached
   (`make_chem_funs.py:148`, `__pycache__/chem_rhs_codegen_<hash>.py`), so it's *loaded*
   not *regenerated* — but it's still exec'd + `jax.jit`-traced every process.
4. The compiled XLA executable is deserialized from the shared persistent cache
   (`JAX_COMPILATION_CACHE_DIR`, set in `vulcan_jax_cli.py:12–18`) on first call — a disk
   read + load every process, not free.
5. A **FastChem subprocess** for the `EQ` initial abundances (`generation.py:1598` sets
   `ini_mix="EQ"`; `ini_abun._run_fastchem`), i.e. a *second* process spawn per profile.

This fixed cost is parallelized across 72 cores but is **paid 100,000 times**. With ~21
distinct grid shapes (`sampling.num_levels_range = [40, 60]`), each new shape also forces
an XLA compile (cached afterward), but every process still reloads the cached executable
from disk.

### What is NOT the problem (already handled)

- **FastChem is not globally serialized.** The emulator copies the `vulcan_jax` package
  into each worker's tree and prepends it to `PYTHONPATH`, so `ini_abun._ROOT` /
  `_FC_DIR` / `.fastchem_lock` (`ini_abun.py:49–52`) resolve to *each worker's own copy*.
  The `fcntl.flock` only serializes within a single worker (which is single-threaded
  anyway). FastChem runs 72-way parallel.
- **chem_funs codegen is not regenerated per profile** on this backend. The
  `regenerate_chem_funs` config flag only affects the `master` backend
  (`generation.py:2053`); the JAX path relies on the content-hash cache.

### Overhead-bound vs compute-bound (must be confirmed first)

The fix only pays off if generation is **overhead-bound**. Measure steady-state
throughput and divide by the worker count:

```
average wall-time per profile ≈ (profiles produced per second) ÷ 72
```

- **~5–10 s/profile** → dominated by the fixed startup above → persistent workers win big.
- **~1–2 min/profile** → dominated by the actual integration → persistent workers barely
  help; only more nodes or a batched-GPU solver would. **Do not build this until the
  measurement shows overhead-bound.**

## Why it's currently a subprocess-per-profile (the constraints to preserve)

The current design is not naive; the subprocess boundary buys two real things that any
replacement must keep:

1. **Per-run config isolation.** `vulcan_jax` is configured by a *module*, `vulcan_cfg`,
   whose globals are patched per run (`generation.py::_patch_vulcan_cfg`). A fresh
   process gives each run a clean module state with no leakage between profiles.
2. **Crash & hang isolation.** A profile that segfaults inside the native FastChem
   binary, blows up memory, or hangs cannot take down the orchestrator — the OS process
   is killed on `vulcan_timeout_seconds` and the spec is retried via the existing
   backfill machinery.

A persistent design must reproduce both, or it trades a throughput win for fragility on a
100k-run job where some profiles *will* misbehave.

## Proposed fix: a pool of persistent worker processes

Keep the OS-process boundary for isolation, but **stop creating a new one per profile.**
Run a fixed pool of `parallel_workers` long-lived worker *processes*; each imports JAX +
`vulcan_jax` and warms the JIT **once**, then consumes a stream of profile specs and runs
each one **in-process**.

```
parent (generation.py)                      worker process  x72  (persistent)
─────────────────────                       ─────────────────────────────────
build sampling plan                         import jax; import vulcan_jax       } once
dispatch spec ─────────────────────────▶    (chem_funs built, cache loaded)
                                            loop:
                                              recv spec
                                              apply per-run cfg (in memory)
                                              RunState.with_pre_loop_setup(cfg)
                                              integ(runstate)   ◀── JIT reused in-RAM
collect per-run HDF5 ◀───────────────────     write raw/runs/run_<id>.h5
                                              send "done <id>"
```

What each profile then costs: only the per-run setup (FastChem EQ + pre-loop) plus the
integration — **no interpreter start, no `import jax`, no re-trace, no XLA reload** for
profiles that reuse an already-seen grid shape.

### Key design decisions

- **Persistent processes, not main-process threads.** The pool members are separate
  processes (`multiprocessing` with the **`spawn`** start method, or a hand-rolled
  pipe/queue pool). This preserves crash/hang isolation. `fork` is avoided — forking
  after `import jax` is unsafe (threads + CUDA state).
- **Per-run config without re-import.** The worker mutates the in-memory `vulcan_cfg`
  module's attributes per profile using the *same* assignment set the current
  `_patch_vulcan_cfg` writes to disk, then calls `RunState.with_pre_loop_setup(cfg)`
  (which already reads cfg at call time). The chemistry network is constant, so
  `chem_funs` is never rebuilt. Requires a careful "reset every varying knob" step so no
  stale global leaks between profiles — this is the main correctness risk and the main
  thing to test. (Cleaner long-term: have `vulcan_jax` accept a config object/namespace
  instead of a module; larger upstream change, optional.)
- **Worker recycling (`maxtasksperchild`-style).** Retire and respawn each worker after
  K profiles (e.g. K≈200) to bound JAX/XLA cache growth and any native leaks. The
  re-import cost is amortized over K runs.
- **Hang handling.** The parent keeps a per-spec watchdog; if a worker exceeds
  `vulcan_timeout_seconds`, the parent **terminates and respawns** that worker and
  re-queues the spec. This reproduces today's subprocess timeout semantics.
- **Crash handling.** If a worker dies (non-zero exit / segfault), the parent detects it,
  re-queues the in-flight spec, and spawns a replacement. Persistent soft failures route
  to the existing backfill (`generation.backfill`).
- **Shape bucketing (optional optimization).** Dispatch profiles to workers grouped by
  `num_levels` so each worker compiles each of the ~21 shapes at most once and reuses it
  in-RAM for the rest of its lifetime.
- **Skip the `.vul` round-trip (bonus).** In-process, the worker already holds the
  `RunState`; it can write the emulator's per-run HDF5 directly instead of pickling a
  `.vul` and reading it back, removing another per-profile I/O hop.

### What changes, what doesn't

- **Changes:** the inner dispatch in `generation.py` — replace the
  `ThreadPoolExecutor` + `subprocess.run`-per-profile with the persistent process pool;
  per-run HDF5 is written by the worker.
- **Requires from `vulcan_jax`:** a clean importable entry point (e.g.
  `vulcan_jax.run(cfg) -> RunState`/output) factored out of `vulcan_jax_cli.cli_main`, so
  the worker can call it in a loop. Small refactor; the CLI would call the same function.
- **Unchanged:** sampling plan + seeding, `raw/runs/` → `raw/chunks/` → `runs.h5`
  consolidation, orphan-promotion resume, backfill, sharding, and the run_gen.pbs
  self-chaining. The on-disk dataset format is identical.

## Expected payoff

If overhead-bound at ~5–10 s/profile of fixed cost, removing essentially all of it (one
import + one warm per ~200 profiles instead of per profile) should cut per-profile
wall-time toward just the integration, i.e. a large multiple in throughput. The exact
factor depends entirely on the integration-vs-overhead split that the measurement above
reveals — this doc does not promise a number.

## Risks / tradeoffs

| Risk | Mitigation |
|------|------------|
| Config leakage between in-process runs | Reset the full varying-knob set each profile; parity-test against the subprocess path (below). |
| Lost crash isolation | Persistent *processes* + detect-and-respawn + re-queue; recycle after K tasks. |
| Hung integration can't be `kill`ed like a subprocess | Parent watchdog terminates+respawns the worker on `vulcan_timeout_seconds`. |
| JAX/XLA memory growth in long-lived workers | `maxtasksperchild`-style recycling. |
| `vulcan_jax` module globals that assume one-run-per-process | Audit for hidden global state before building (open question below). |

## Validation plan (before flipping the default)

1. **Parity:** generate the same N≈500 specs (fixed seed) through both the subprocess
   path and the persistent path; assert the per-run HDF5 outputs match within the
   existing numerical tolerances. This is the gate — the dataset must be identical.
2. **Throughput:** measure profiles/hour on one GH200 node, persistent vs subprocess, at
   `parallel_workers=72`, to confirm the win is real (and to compare against the
   oversubscription quick-fix `parallel_workers≈96`).
3. **Robustness:** inject a deliberately failing/hanging profile and confirm the worker is
   respawned, the spec is re-queued, and the run completes.

## Rollout

Gate behind a config flag, e.g. `generation.worker_mode: "subprocess" | "persistent"`
(default `"subprocess"`), so the change is opt-in and trivially reversible. Ship only
after the parity test passes.

## Open questions to resolve first

1. **Is generation actually overhead-bound?** (the per-profile wall-time measurement) —
   gates whether this is worth building at all.
2. Does `vulcan_jax` carry per-run global state beyond `vulcan_cfg` that would leak across
   in-process runs (module-level caches keyed on cfg, the photo/ion setup, FastChem I/O
   files written to fixed paths in the package dir)? FastChem writes
   `input/vulcan_TP/vulcan_TP.dat` and `output/vulcan_EQ.dat` inside `_FC_DIR`
   (`ini_abun.py:72–75`) — in a persistent worker these are reused/overwritten per
   profile and must be confirmed race-free within a single worker (they are, since a
   worker is sequential) and isolated across workers (separate package copies — keep that).
3. Is the cleaner `vulcan_jax.run(cfg_object)` API worth doing now, or is in-place
   `vulcan_cfg` mutation acceptable for the first version?
4. Interaction with the batched-GPU generator (separate proposal): persistent CPU workers
   and a GPU batch path are not mutually exclusive, but we should pick one to build first
   based on the measurement.
